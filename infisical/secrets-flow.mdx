Secrets never touch git and there is no ansible-vault. Instead, every tofu and ansible invocation is
wrapped in `infisical run`, which fetches the pinned project/environment secrets and injects them as
environment variables into the child process. tofu and ansible then each read those variables in their
own way.

```text
Infisical (project/env/folder)
        │  infisical run --
        ▼
environment variables in the child process
        ├── tofu    → TF_VAR_<name>  auto-maps to  variable "<name>"
        └── ansible → {{ lookup('env', 'NAME') }}
```

## `infisical run --` injects the secrets

`infisical run -- <cmd>` resolves the secrets for the selected project/environment/folder and runs
`<cmd>` with them present as env vars. The `just` recipes wrap this for you, so you rarely type it raw:

```bash
# what `just tf-apply cloud` runs under the hood, inside tofu/cloud/
infisical run -- tofu apply

# what `just ansi-core apw1` runs, inside ansible/core/
infisical run --env=apw1 --path=/agent -- ansible-playbook site.yml
```

The project and environment come from the `.infisical.json` pinned in each root/project directory
(see [Projects](/infisical/overview)), unless you override them with flags.

## tofu: `TF_VAR_<name>` auto-maps to `variable "<name>"`

tofu treats any environment variable named `TF_VAR_<name>` as the value for the input `variable "<name>"`.
So a secret stored in Infisical as `TF_VAR_ANSI_CLOUDFLARE_API_TOKEN` lands as an env var of the same
name, and tofu wires it straight into the matching variable — no `-var` flags, no `.tfvars` file:

```hcl
# declared in the tofu root
variable "ANSI_CLOUDFLARE_API_TOKEN" {
  type      = string
  sensitive = true
}

# used by the provider — value comes from TF_VAR_ANSI_CLOUDFLARE_API_TOKEN
provider "cloudflare" {
  api_token = var.ANSI_CLOUDFLARE_API_TOKEN
}
```

<Tip>
  This is why tofu credentials are stored with the `TF_VAR_` prefix in the `infrastructure/prod` project
  (`TF_VAR_EXCLOUD_API_KEY`, `TF_VAR_EXCLOUD_ORG_ID`, `TF_VAR_ANSI_CLOUDFLARE_API_TOKEN`). The prefix is
  the contract that makes the auto-mapping work.
</Tip>

## ansible: `lookup('env', 'NAME')`

ansible reads the injected variables explicitly with the `env` lookup plugin. The `group_vars` files map
each secret to a play variable:

```yaml
# ansible/core/group_vars/core.yml
ansible_host: "{{ lookup('env', 'TARGET_IP') }}"
ghcr_token:   "{{ lookup('env', 'GHCR_TOKEN') }}"
deployment_id: "{{ lookup('env', 'DEPLOYMENT_ID') }}"
enroll_token:  "{{ lookup('env', 'ENROLL_TOKEN') }}"
allow_acme_dns: "{{ lookup('env', 'ALLOW_ACME_DNS') | default('false', true) | bool }}"
```

Because the value is looked up by name, the secret must actually be present in the process environment —
which brings us to the flags that decide which secrets get injected.

## The flags: `--env`, `--path`, `--projectId`

| Flag | Purpose | Default |
|------|---------|---------|
| `--env <env>` | Selects the environment (`prod`, `production`, `apw1`, `dev`…) | from `.infisical.json` |
| `--path <folder>` | Selects the secret folder within the env | `/` |
| `--projectId <id>` | Targets a project that has no `.infisical.json` pin | from `.infisical.json` |

`--env` is how you pick which core VM you are provisioning: the `vritti-core` project stores each VM's
secrets under a different env, and the inventory holds no per-host data, so `just ansi-core apw1` versus
`just ansi-core dev` differs only by the `--env` value.

`--path` selects the folder. It **defaults to `/`**, but the core agent secrets live under `/agent`, so
core runs must pass `--path=/agent`.

<Warning>
  For `ansi-core`, `--path=/agent` is **required**. The core agent secrets (`DEPLOYMENT_ID`,
  `ENROLL_TOKEN`, `TARGET_IP`, `GHCR_*`, `ALLOW_ACME_DNS`) live under `/agent`, not the root path. Omit
  `--path=/agent` and Infisical resolves the empty root folder — every `lookup('env', ...)` comes back
  empty, `ansible_host` is blank, and the play fails to connect with no obvious cause. The
  `just ansi-core <env>` recipe bakes `--path=/agent` in for exactly this reason; only raw
  `infisical run` invocations are exposed to the gotcha.
</Warning>

`--projectId` is for reaching a project that isn't pinned locally. The `cloud_stack` role uses it to
export the `vritti-cloud/production` app env — that project has no `.infisical.json`, so the role passes
`--projectId={{ vritti_cloud_project_id }}` (from `ANSI_VRITTI_CLOUD_PROJECT_ID`) along with `--env` and
`--path` to `infisical export`.

## What this buys us

- **Nothing committed.** No secrets, no `.tfvars`, no vault files in git.
- **No ansible-vault.** Secret material only exists in the process environment during a run.
- **One source of truth.** Rotating a secret in Infisical changes it everywhere on the next run.
