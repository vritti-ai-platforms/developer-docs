Vritti runs on a small, deliberately boring estate: **one cloud control-plane VM** and a set of
**agent-managed core VMs**. Everything is infrastructure as code, everything is driven by `just`, and
every secret flows through a self-hosted Infisical.

## The shape of the platform

- **`vritti-cloud`** — the control-plane VM. It sits behind Cloudflare and runs the cloud compose stack:
  nginx, the cloud API (`cloud-server`), the cloud-web SPA, Postgres, Redis, NATS, DbLab, and a
  cloudflared tunnel. It also hosts the **dev core**.
- **Core VMs** (e.g. `apw1`) — direct-served customer/core deployments. Each runs the
  `vritti-application-agent`, which pulls a cloud-signed **desired state** from `api.vrittiai.com` and
  reconciles the core stack (core-server, commerce-service, Postgres, Redis, NATS, nginx, gitea).
- **Two DNS zones** — `vrittiai.com` (cloud + prod cores) and `vrittiai.dev` (the dev core).
- **Three Infisical projects** — `infrastructure`, `vritti-cloud`, and `vritti-core` — the single source
  of truth for every credential and per-VM value.

## How it is operated

All infrastructure lives in one repo, `infrastructure/`, and is driven by `just` recipes that wrap
OpenTofu and Ansible in `infisical run` so secrets arrive as environment variables. Nothing sensitive is
committed; there is no `ansible-vault`.

```bash
just tf-apply network    # reserved IPs, DNS, tunnels, shared security group
just tf-apply cloud      # the control-plane VM
just ansi-cloud all      # provision the cloud host + compose stack
just ansi-core apw1      # bootstrap a core VM + deploy/enroll the agent
```
